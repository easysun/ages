# Formal Timeline Performance Measurement Protocol

## Goal and status

Define reproducible evidence for the existing Timeline performance gate: 100 interactive story items and a separate 10,000-item chronological overview, with p50/p95 input-to-next-paint and presented-frame intervals, mounted-media counts, and raw evidence. This document does not capture or qualify a device. The current Chromium pilot remains diagnostic, and the physical-device gate remains open.

The offline analyzer and separately reviewed synthetic Playwright Chromium method runner are implemented. The method pilot is limited to local desktop Chromium and cannot satisfy the physical-device matrix. Runtime verification and the full repository gate are tracked in the implementation plan.

## Required device and workload matrix

- **Desktop:** one actual Mac running the already-installed Brave browser; record its exact version and capture the Mac model, chip, memory, macOS build, viewport, device scale factor, and active display refresh rate at capture time. Do not install or switch desktop browsers for this measurement.
- **Phone:** actual Samsung Galaxy S25 Ultra, Android 16, One UI 8.5; run Chrome, Samsung Internet, and Brave separately and record each exact version.
- **Workloads:** run the 100-item interactive story and the 10,000-item chronological overview as separate cases. Do not combine their sample groups.
- **Actions:** open, Fit all, pan, zoom, resize, append, and scroll. Each action has its own trial boundaries and results. Reset the synthetic fixture to its exact baseline between trials; setup and cleanup are outside measured windows.
- **Repetitions:** for each device/browser × workload × action cell, run three independent sessions with 40 measured repetitions per session (120 planned). The three-session layout exposes session-to-session variation; 120 is a chosen repeatability convention, not a statistically derived sample-size guarantee. Perform five unmeasured warm-ups per action per session. Across one Mac/browser and one phone with three browsers, the matrix schedules 6,720 measured trials plus 840 warm-ups. Do not stop early when the valid-sample minimum is reached.
- **Quantiles:** sort qualified raw durations ascending. Use nearest rank with one-based rank `ceil(p × n)` and no interpolation: p50 is rank `ceil(0.50 × n)`, p95 is rank `ceil(0.95 × n)`. The 100-valid-sample minimum applies to the pooled 120-trial cell, not an individual 40-trial session. Report per-session planned/valid/missing/censored/invalid counts as diagnostics, plus one pooled same-cell p50/p95. Never pool across device/browser, workload, or action.

For each planned trial and metric, assign exactly one status: qualified-valid, missing/unsupported, censored, or invalid, with a reason code. A qualified-valid duration has a trusted initiating input, a source whose endpoint semantics are proven for that browser, an exact event identity, and a loss-free trace. Compute an observed nearest-rank summary only from qualified-valid durations when there are at least 100. It is **formal** only when the source is validated as complete for the target population and all 120 planned trials are qualified-valid; otherwise label it `OBSERVED_ONLY` diagnostic, even if it has 100 values. Missing, censored, and invalid trials remain in the counts and are excluded from the duration distribution. Thresholded Event Timing entries are always observed-only for unrestricted interactions because short and excluded continuous events are censored/unsupported.

For presented-frame intervals, a valid trial must have a recognized action stimulus, a declared active window, and a loss-free trace. Pool intervals only within the same device/browser × workload × action cell. Require at least 100 valid trials and 100 qualified adjacent-frame intervals before reporting interval p50/p95; preserve the three session counts separately. Formal interval status additionally requires complete source coverage for all 120 planned active windows; otherwise label it `OBSERVED_ONLY`. These intervals are serially related, so the quantiles are descriptive and do not imply 100 independent trials. Do not extend gestures or active windows, or bridge idle time, to manufacture more intervals. Report `NO_ADJACENT_PRESENTED_FRAME` when a valid trial has no adjacent presented endpoints and `INSUFFICIENT_VALID_SAMPLES` when the cell has fewer than 100 qualified intervals.

The 100-duration and 100-frame-interval minima are pre-capture reporting rules, not claims of statistical power. A smaller group reports its counts and `INSUFFICIENT_VALID_SAMPLES`, with no scalar p50/p95.

## Metric definitions and source limits

### Input to next paint

The formal browser API candidate is `PerformanceEventTiming.duration` for a trusted input entry, grouped by nonzero `interactionId` where the browser assigns one. It represents the event timestamp through the next rendering update after event dispatch. For an interaction group, retain the maximum event duration as the interaction sample and retain each underlying event record for audit. Record event type, start time, processing start/end, duration, interaction ID, target selector when exposed, entry type, and the configured observer threshold.

This API does not provide a complete, precise series by itself. The W3C Event Timing draft rounds durations to 8 ms, exposes ordinary `event` entries only at a minimum 16 ms threshold, and excludes continuous `pointermove`, `touchmove`, `pointerrawupdate`, `wheel`, and `mousemove` events. A missing API entry is not zero. Record scheduled trials, trusted target-event dispatches, returned entries, threshold-censored entries, unsupported event types, and invalid/missing samples separately. Report an observed-only percentile as diagnostic; it does not represent all interactions unless the method pilot establishes a complete sample source for that group. Do not infer hidden durations or interpolate them.

The original pilot has legacy EventTiming spans but no modern latency records and cannot prove fallback-free endpoints. The subsequent 14-case method pilot records Chromium 153.0.8010.12 and modern EventProcessing payloads, but exported pointer flows and frame_index are absent. Its supported alternative is the exact same-entry crosswalk below; proximity and reused parent-track membership never establish identity.

#### Observed discrete-entry crosswalk

Scope this method to the observed Chromium 153.0.8010.12 shape and pinned source revision 971a7443b0c9b0a9b2860529b33331b76077ec62. Keep raw bytes unchanged. Pair closed legacy EventTiming and modern EventProcessing b/e slices within their own process/category/typed-track lifetimes, with stable timestamp ordering and original-array tie breaks. Distinguish id, id2.local and id2.global scopes. Reject mismatched, overlapping nonnested or incomplete slices; payload-free modern n markers cannot qualify.

Require legacy data fields type, frame, nodeId, cancelable, interactionId, interactionOffset, timeStamp, processingStart and processingEnd, plus integer absolute begin/end timestamps. Require modern event_timing fields type, frame, node_id, cancelable, interaction_id and interaction_offset, plus explicit fallback_reason and fallback_time. Parse integer identities/timestamps losslessly.

Invert each legacy relative-millisecond number using Chromium's exact binary64 conversion double(integerMicroseconds)/1000. Retain the original decimal token and its correctly rounded finite binary64 value. Find the nearest integer to the exact decimal token multiplied by 1000 and examine that integer and its immediate neighbors. Accept exactly one preimage with absolute value at most 2^40 whose forward binary64 conversion equals the decoded value exactly. Never use an epsilon. Derive origin=legacyBegin.ts-recovered(timeStamp) separately per entry and require consistent origin within an explicit capture/document scope (case, renderer PID and frame), separated across navigation/document replacement.

Match by exact PID, TID, absolute processing start/end, explicitly mapped type, frame, node, cancelable and interaction ID/offset, uniquely in both directions. Modern interaction ID/offset must be integers in [0, 2^32-1]; legacy representations must be integers in [-2^31, 2^31-1], with negative values normalized by adding 2^32 only after range validation. Recognize observed optional pointer_id/key_code without making them crosswalk keys. Do not wrap node IDs, timestamps or track IDs. Initial discrete mappings are click/CLICK_EVENT, pointerdown/POINTER_DOWN_EVENT, pointerup/POINTER_UP_EVENT, keydown/KEY_DOWN_EVENT and keyup/KEY_UP_EVENT. Other explicitly mapped types may be diagnostic only; unknown types are rejected.

A unique match proves presentation only with fallback_reason exactly None, integer fallback_time zero and absent event_timing.fallback_time_us. Reject contradictory, nonzero, unknown or missing fallback evidence. The pinned GetEndTime source then makes the closed legacy end the same entry's presentation endpoint. Report exact latency end-begin in microseconds and processing-end-to-presentation separately; API rounding and observer thresholds do not apply to these trace spans.

An individually complete entry does not require a closed EventsInAnimationFrame group, whose endpoint is commit/fallback rather than presentation. Incomplete groups prohibit group-dependent aggregation; reused parent tracks do not establish frame membership. Action samples additionally require explicit target-document/window attribution and a predeclared stimulus/event rule. Incidental events remain diagnostic. Separate cold-open activation from secondary Chronological activation and immediate input latency from asynchronous completion. Continuous pan, wheel/pinch zoom, scrolling and resize cannot borrow incidental discrete entries.

Task 4 first reports sanitized method candidates and rejection counts. It must not promote candidates to formal action trials when attribution, interaction aggregation, browser-source completeness or modality equivalence is unproved. Source agreement does not attest a vendor binary's patch identity; the physical-device gate remains open.

Keep the existing `MouseUp → EventLatency → STATE_PRESENTED_ALL` value named **input-to-presented-frame**. It is a separate diagnostic metric. Do not rename it to input-to-next-paint or claim equivalence based on matching durations, timestamps, or a nearby frame. Any cross-source join must use a verified exact event/flow identity; timestamp proximity is not a join key.

For open, the primary qualifying stimulus is the actual Timeline route activation from the Timelines list for both workloads. Retain the complete initial version-pinned projection fetch and index build in the trace; the current editor loads that projection before its Story view is ready. Record immediate input-to-next-paint separately from projection-ready completion. In the 10,000-item case, then activate the actual Chronological mode button and record that secondary input and its render window separately; final operation completion requires the complete chronological overview to be visible. Do not pool this secondary input into the primary open next-paint distribution, or substitute a preloaded mode-switch duration for cold opening. For append, record immediate input-to-next-paint separately from operation completion: the definitive committed response followed by the appended item appearing in the refreshed view. Completion durations start at the declared primary input and end at explicit completion markers; they never replace or extend immediate next-paint samples. Resize and continuous scroll/pan/zoom are reported only for a source proven to cover their initiating input. If no such source exists, keep that action/metric cell unavailable and the gate open.

### Presented-frame intervals

Use the closing timestamp of each uniquely paired `STATE_PRESENTED_ALL` `PipelineReporter` as that frame endpoint. Identify a frame by the exact `(surface_frame_trace_id, display_trace_id)` pair and attribute it to the exact `(rendererPid, layerTreeHostId, frameSource)` stream. An interval is the raw positive delta between adjacent unique presented-frame endpoints within one declared action and one explicit active window. Never bridge a stream, action, active-window boundary, or trace boundary.

An active window is an explicit half-open trace-time interval `[startUs, endUs)` during which the action is actively driving visual updates. Captures declare separate windows around pauses, data waits, and idle periods; analysis does not infer activity from frame rate or a guessed idle timeout. A frame endpoint must fall within the window. Report interval samples in microseconds, their p50/p95, source counts, and rejected interval counts. Do not convert them to FPS or use an FPS/latency pass threshold.

### Mounted media

At baseline and after one standardized viewport scroll, count currently mounted `<img>` and `<video>` nodes inside the Timeline separately. Take the post-scroll count after the action's next rendered update and the media observer has applied its mount/unmount work; record the observation point. Counts describe mounted elements, not downloaded bytes or decoded frames. The 10,000-item overview should mount no media. Keep screenshots or DOM snapshots out of raw trace reports unless separately requested.

## Capture controls and evidence retention

Every capture manifest records, at capture time: run ID and UTC start/end; source revision; fixture revision and exact row count; dataset mode; device and OS details; browser product/version; viewport, screen, DPR, and refresh rate; cache state; input method; session and trial counts; action and active-window bounds; renderer PID and frame stream identity; enabled trace categories; data-loss status; and the raw trace basename, byte size, and SHA-256. Hardware details observed only during preflight do not qualify as capture-time metadata.

Keep each original trace byte-for-byte in its local run directory. Compute and record SHA-256 before analysis and verify it again afterward. Do not rewrite, check in, or copy raw user media or trace payloads into repository fixtures. The report contains only selected metadata, sample values, counts, digests, and reason codes; it excludes URLs, captions, asset details, IDs from the product database, and unrelated trace arguments. Any unsupported event shape, missing endpoint, ambiguous identity, or trace data loss produces an explicit reason and no formal sample.

Phone capture remains a user-supplied gate through an approved supported workflow. This protocol does not use `chrome://inspect`, ADB, CDP, a substitute browser, or an SDK installation to reach the phone. No phone capture is part of the synthetic pilot.

## Offline analyzer protocol-group contract

The analyzer accepts optional `protocolGroups` for predeclared cells. If present, the array contains 1–56 groups. Each group has only `deviceKey` (`mac` or `s25-ultra`), `browserKey` (`brave`, `chrome`, or `samsung-internet`; Mac permits Brave), `workload` (`100-interactive` or `10000-chronological`), a canonical action, `plannedTrials: 120`, three sessions numbered 1–3 with 40 planned trials each, and up to 120 non-valid trial entries. A trial entry has only its session and trial number, `status` (`missing`, `censored`, or `invalid`), and a fixed reason: `NOT_CAPTURED` or `UNSUPPORTED_INPUT` for missing; `TRACE_TRUNCATED` or `ACTION_INCOMPLETE` for censored; `TRACE_DATA_LOSS`, `AMBIGUOUS_CORRELATION`, or `MALFORMED_TRACE` for invalid. Omitted trials without a linked segment are missing. Duplicate cell keys and duplicate trial references are rejected.

A segment links a valid candidate trial with `protocolGroupIndex`, `session`, and `trial`; linked segments accept only documented fields and require exact trace/action/renderer/layer/frame-source identity and one or more explicit active windows. Each segment has at most 120 windows; window IDs use 1–64 ASCII letters, digits, underscores, or hyphens and are not echoed. A window is a half-open `[startUs, endUs)` interval contained in its segment, with windows sorted and non-overlapping. Linked windows in the same trace cannot overlap, preventing a frame from being counted twice. At most 6,720 measurement segments are accepted in one manifest. A presented-frame interval must have both endpoints in the same window and exact stream. Fully consistent repeated records for the same exact frame pair, endpoint, renderer, compositor stream, and presented state are deduplicated once. Conflicting endpoint or stream reuse, or reuse of one frame identity across distinct active-window/trial contexts, invalidates every affected linked trial as `invalid/AMBIGUOUS_CORRELATION`; the analyzer discards that trial's intervals rather than bridging around the conflict. A malformed reporter identity or endpoint maps to `invalid/MALFORMED_TRACE`, trace data loss or unknown loss status maps to `invalid/TRACE_DATA_LOSS`, and a linked window with no matched reporter maps to `missing/UNSUPPORTED_INPUT`. These derived statuses share the same fixed 120-trial and 40-trial session counts as manifest-declared statuses; there is no extra unqualified status bucket. Group summaries derive qualified frame trials and intervals only from loss-free linked traces containing an exact presented reporter, and report manifest-declared plus derived non-valid counts; they do not accept durations or a manifest proof flag. Existing input-to-presented-frame diagnostics never qualify a next-paint trial. Until Task 4 proves an exact next-paint source, every group's next-paint result remains unavailable with `NEXT_PAINT_METHOD_UNPROVEN`.

## Method-discovery pilot

Before hardware runs, review and execute one bounded local Playwright Chromium pilot on the 100-item and 10,000-item fixtures. Capture one measured example of each required action, with trace categories needed for both `latency` EventTiming records and the existing input/frame records. Include a delayed open and append so immediate paint and asynchronous completion have distinct markers. Include continuous pan, wheel/touch-style scroll stimulus supported by the local desktop harness, and viewport resize. The run is synthetic diagnostic evidence only.

Before implementing quantile code, probe the existing raw traces and pinned source for the category and field shapes above; record that the existing traces have no modern latency records and cannot qualify legacy endpoints. The separately reviewed method pilot must answer, with raw evidence:

1. Whether the observed legacy/modern exact entry crosswalk establishes explicit no-fallback presentation evidence; absent exported flows must not be invented.
2. Whether exported frame-group evidence proves membership/completeness; absent frame flows or frame_index leave group-dependent aggregation unavailable.
3. Whether the reported API `duration` and trace endpoint use the same event identity and endpoint semantics in this Chromium build. If exact association or endpoint proof is absent, reject equivalence.
4. Which exact Chromium input/flow identities cover continuous action updates and which exact frame reporter belongs to each event. Unsupported scroll, resize, pan, or zoom input types remain explicitly unavailable.
5. Whether active-window and frame-stream metadata are sufficient to exclude idle gaps and cross-stream intervals.

Pin the inspected Chromium source revision and record the tested binary version. Source agreement does not prove a vendor browser binary is identical. After method review, repeat the support check independently for Chrome, Samsung Internet, and Brave; do not assume their trace schemas match Chrome.

## Acceptance and open gates

The offline analyzer must calculate nearest-rank p50/p95 only when the predeclared minimum is met, report valid/planned/censored/missing/invalid counts, preserve all accepted raw sample values, reject cross-stream or cross-window intervals, and keep unsupported EventTiming spans diagnostic. The original pilot remains unqualified because it lacks modern latency evidence and declared active windows. The subsequent 14-case run has modern records but remains synthetic method evidence and does not satisfy physical acceptance.

The formal Task 6 gate closes only after every required device/browser × workload × action cell has the required loss-free raw evidence, capture-time metadata, 120 qualified input trials, at least 100 qualified frame intervals across all 120 active windows, explicit missing/censored/invalid counts, active-window intervals, and mounted-media counts. The 100-valid-sample floor permits diagnostic percentile output; it does not waive the completeness rule for a formal result. A method gap or missing cell leaves the gate open; no device or action is silently dropped. If a discrete action yields fewer than 100 intervals, preserve the actual result and its reason code; do not alter the action or include idle frames to meet the floor.

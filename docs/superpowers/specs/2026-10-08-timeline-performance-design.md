# Timeline Viewport Performance Design

## Goal and scope

Close the story-mode viewport performance gates for 100 fully interactive items and a separate 10,000-record lightweight overview. Preserve the current 100-item keyboard/touch editing and reorder flow, manual framing, captions, `event_at`, `position`, optimistic version checks, privacy, and moderation behavior. The 10,000-record case is an ordered browse-and-describe workflow; it does not introduce a 10,000-ID reorder request. Chronological overview remains a separate open design requirement.

Assumption: a complete accessible ordered editing workflow means every item can be reached in narrative order, its caption/date can be edited, and its media is available when brought into view. For stories above the existing 1,000-ID order limit, order remains readable but is not editable through the current reorder contract.

## Current code and gap

`GET /api/timelines/:id` is authenticated and owner-scoped, but returns every full item. The editor also requests `/api/assets/:id` once for every missing item asset. `Moment` renders an image or video for every item; `loading="lazy"` and `preload="none"` defer transfer, not DOM mounting. `StoryViewport` scans every supplied position on every render. Finally, every `mutateTimeline()` response selects and returns the complete item array, so append and edit would remain unbounded for large stories.

The existing order mutation accepts at most 1,000 IDs. The 100-item browser workflow already covers keyboard/touch movement and refresh persistence. Those behaviors stay intact.

## Alternatives and decision

1. **Extend the existing full detail response with optional paging.** This mixes full editor records with overview data and makes existing response shape and completeness ambiguous.
2. **Add an owner-authorized overview read and a bounded editor-page read; keep full detail for compatibility.** This cleanly separates marker data from editable details and permits staged adoption.
3. **Add client-side virtualization only.** This reduces mounted DOM/media but still downloads all item details and performs unbounded metadata requests.

Choose option 2, with real media unmounting in the client. It fits the current Hono route, owner checks, D1 keyset ordering, and versioned mutations. Use existing React/browser APIs; add no dependency.

## Read contracts

Keep `GET /api/timelines/:id` and its existing full representation unchanged for compatibility. The editor uses the new reads below for all stories.

`GET /api/timelines/:id/overview?limit=1000&cursor=…` returns a timeline summary, exact item count, a page of `{ id, position }`, and `next_cursor`. A first-page read may omit `version` to select the current snapshot or supply it to require a specific snapshot; summary, count, and rows are captured in one D1 read batch, and the response supplies the snapshot version. A continuation cursor is exclusive after its `(position, id)` pair and requires that version. For a bounded jump/tail read, accept `from_position` and `from_id` together as an inclusive lower bound and require `version`; reject an incomplete pair or any request combining a cursor with a lower bound. Cursors are bound to the timeline. Use keyset ordering and `LIMIT limit + 1`; validate `limit` from 1 through 1,000. Rows contain no caption, asset metadata, or media URL.

`GET /api/timelines/:id/items?version=N&limit=100&cursor=…` returns at most 100 ordered editor records with `id`, `asset_id`, `position`, `caption`, and parsed `event_at`, plus a safe nested asset summary (`id`, `kind`, `original_name`, `width`, `height`, `duration_ms`). Require `version`; validate `limit` from 1 through 100. A `cursor` continues exclusively after its `(position, id)` pair. For a first page or a jump from the overview index, accept `from_position` and `from_id` together as an inclusive lower bound; reject a request that supplies both a cursor and a lower bound. Join assets in this bounded query; do not fan out to `/api/assets/:id` for each item. Keep the existing single cover-asset lookup and library picker behavior.

Both routes use the existing authenticated `timelines` router and require `timeline.owner_id` to equal the signed-in user. Return 404 for another owner, as the current detail route does. For every continuation, lower-bound, and detail request, use one D1 read batch containing the owner-scoped timeline/version row and the requested page projection; include the count in that batch when returning it. Compare the requested version with the timeline row from that same batch and discard the projection with 409 on mismatch. Never check the version in one query and read page rows in a later independent query. This gives each accepted page one coherent snapshot. Use the same owner view of moderated content as the current detail endpoint; do not route through or loosen public visibility checks. Public timeline and media routes are unchanged. Responses remain `no-store` under request middleware.

Every page is pinned to one timeline `version`. A later page whose requested version differs from the current row returns the existing `CONFLICT` (409) without rows; the client reloads the overview and keeps any unsaved form draft. A successful write increments the version exactly once. The client advances its local version after success and may reuse a keyset cursor only when the operation leaves the order keys valid. Reorder is allowed only when `total_items <= 1000`, where the client has the complete ID index and can submit the existing complete unique order. Above 1,000, hide move controls and announce that narrative order is read-only; caption/date edits, remove, append, and ordered navigation remain available.

## Bounded writes and editor behavior

Preserve today’s mutation response by default. Add opt-in `Prefer: return=minimal` for editor writes: return 204 only after the version-gated transaction commits and skip the full-item SELECT. Treat a received 204 as definitive success. Capture the submitted `expected_version`; record the committed version as exactly `expected_version + 1` before starting any reconciliation read. Keep that committed version separate from the displayed/read version, and never increment whichever version happens to be current when an asynchronous read finishes. `api()` must handle a 204 without attempting JSON parsing.

For append, query `/overview` with `version=expected_version+1`, `limit=2`, and an inclusive `from_position`/`from_id` pair for the last known item; for an empty story, request the first row at that version. Verify the nonempty response begins with the anchor, discard that duplicate anchor when merging, add only unseen IDs, and replace the cached count with the response count. The empty-story response must contain the newly appended row and count 1. This makes a confirmed append reconcile with one bounded read.

Track mutation commitment separately from reconciliation. Once 204 arrives, remove that asset from pending picker selections and mark it added, even if the tail read later fails. Never replay the committed append because the tail read failed or returned 409. If a picker batch contains more assets, stop its append loop at the first unreconciled 204; leave later, uncommitted selections pending and unsent. If reconciliation fails or another writer advances the version before the tail read, pause all writes, retain the committed status and all unrelated drafts/selections, and show a “refresh before continuing” state. Start reconciliation with an overview first-page request that omits `version`, then load every overview page and the active detail window at the version returned by that first page. Rebind drafts before enabling writes. If any page is stale or fails, keep writes paused and offer refresh retry; do not retry the append. After reconciliation the user may deliberately add the same asset again. A received 409 from the mutation itself means that write did not commit; reload while preserving drafts and do not treat it as an append success.

For edit/remove/order, update the loaded detail/index data from the submitted change after 204. A 409 still triggers the current draft-preserving reload behavior. On any failed or stale page read, retain local commit state and drafts until a current-version overview and the needed detail window load successfully.

Load all 10,000 overview rows as at most ten 1,000-row pages before presenting a complete marker overview; show loading progress while pages are outstanding. Keep only `{id, position}` for that index. Render marker groups from the visible position range using binary search into the sorted index, then group visible points into the existing 48-pixel bins. Do not scan all 10,000 records on every pan/zoom render. The viewport receives the full first/last position bounds for initial fit and Fit all. A manual view remains in place across resize, append, page loading, and detail-window changes; navigation to another timeline resets it. Viewport input never writes `position`, `event_at`, or `version`.

Keep the semantic editor as an ordered list. For up to 100 items, show all controls in the existing list, preserving the current keyboard/touch move buttons and complete order payload. For larger stories, render at most 100 full editor records at once, with accessible previous/next range controls and a labeled “go to moment” ordinal input. Each list item exposes its ordinal and total set size; changing ranges moves focus to a named range heading, while saving a field keeps focus on that field. This gives keyboard and screen-reader users access to every item without mounting 10,000 forms.

Own unsaved drafts at the editor level in a map keyed by stable item ID, separate from the fetched record window and media. Store caption, event kind, date or instant value, time zone, and dirty state. Overlay drafts whenever a detail page loads. Leaving and returning to a window, a 409 reload, and a local or remote reorder must not clear a draft; after an order refresh, locate the item by ID and keep focus on its field, opening the range containing it if needed. Clear a field draft only after a confirmed save of the same submitted value; typing made while that save is in flight remains dirty. If a refreshed index no longer contains a dirty item, move its draft to an accessible “Item removed elsewhere” area, retain all values, disable save, and allow the user to copy or deliberately discard it. A local remove of an item with dirty fields requires an explicit discard confirmation. Never silently discard a dirty draft.

Preserve ordinary page scrolling, browser magnification, reduced-motion behavior, readable labels, and visible focus.

Mount `<img>` and `<video>` elements only for media cards intersecting the document viewport plus one viewport of vertical overscan. Keep a sized placeholder using known dimensions, or a stable minimum media box when dimensions are absent. Unmount media when it leaves that band; `loading="lazy"` and `preload="none"` may remain as secondary network controls. If `IntersectionObserver` is unavailable, keep media unmounted and expose a focused, accessible “Load media” action instead of mounting every item. The overview never mounts media.

## Binary checks and measurement protocol

Define these pass/fail checks before implementation:

- A synthetic owner timeline of 10,000 items returns exactly 10,000 unique, strictly ordered overview IDs across pages of at most 1,000; no caption or asset payload is present. Another owner receives 404. Change the version before a continuation, inclusive overview read, and editor detail read in separate cases; each returns 409 with no mixed-version page. Assert each request checks version and reads its projection in the same D1 batch.
- A detail-page request returns at most 100 items and one joined safe asset summary per returned item. The 10,000-item editor makes no per-item asset-detail fan-out and no full-detail request. A successful `Prefer: return=minimal` write returns 204 without an item array; a stale write returns 409. For nonempty append, the inclusive tail read returns the previous last row and new row; the client deduplicates the anchor and replaces the count. For empty append, it returns the new first row and count 1. Private/unlisted owner access and public moderation gates remain unchanged.
- The existing 100-item keyboard/touch reorder, caption/date save, conflict-draft, and refresh-persistence scenarios still pass. In a story above 100 items, parameterize a dirty draft with both calendar-date and instant event kinds; edit its caption, kind, value, and time zone, leave the window, return, and assert every value remains. In a story at or below 1,000 items, cause a local reorder and a separate 409 with a concurrent reorder that moves a dirty item to another window; assert the same caption, kind, date/instant value, time zone, and focused field survive both. Remove a dirty item remotely; assert its draft remains in the unresolved area until deliberate discard. A 10,000-item fixture can visit the first, middle, and last edit windows by keyboard and touch; every reachable record retains its caption/date and ordinal. No reorder request over 1,000 IDs is sent.
- After an append receives 204, fail the tail read and separately advance the version with a concurrent title mutation so the tail read returns 409. In both cases assert the user's append appears exactly once, no automatic replay occurs, the committed asset is no longer pending in the picker, unrelated selections/drafts remain, and further writes stay disabled until a current overview and detail window reconcile. A 204 commits `expected_version + 1` even when its tail read fails; a 409 from the write itself does not commit.
- With a deterministic 100-card media fixture and fixed viewport/card dimensions, mounted `<img>`/`<video>` elements never exceed the cards intersecting the viewport plus the configured one-viewport overscan. Scrolling away removes those elements; overview markers and offscreen cards have none mounted. Pan/zoom/render work visits only the visible marker range plus its groups.
- Initial fit, Fit all, pan, zoom, resize, and detail-window navigation do not mutate saved `position`, `event_at`, or `version`. An explicit append creates the expected new item at the server-assigned next position and increments version once; it preserves the prior manual viewport frame. Browser checks retain focus, reduced motion, vertical scroll, and page magnification behavior.

For performance evidence, run both the 100-item interactive case and 10,000-record overview on at least one explicitly named desktop device/browser and one explicitly named phone/browser. Record exact hardware model/chip and memory, OS build, browser name/version, viewport dimensions, device scale factor, display refresh rate, fixture revision, and whether the cache is warm. Execute the same open, Fit all, pan, zoom, resize, and append scenario; retain raw traces and report p50/p95 input-to-next-paint and frame intervals, plus mounted image/video counts before and after scrolling. Report measured values without inventing an FPS or latency pass threshold. Missing environment names, raw measurements, or media counts means the evidence gate is incomplete.

## Not implemented and proof gaps

This is a design only; no routes, client behavior, fixtures, tests, or hardware measurements have been added or run. Synthetic browser fixtures alone will not prove the production D1/Worker path; the integration gate must seed 10,000 rows in local D1 and exercise authenticated paging and stale-version handling. Named-device measurements remain outstanding until implementation. Chronological overview, including date-only precision, time zones, and undated items, remains open and is not covered or waived here.

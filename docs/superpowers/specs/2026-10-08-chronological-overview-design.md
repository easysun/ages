# Chronological Timeline Overview Design

## Decision and dependency

Add a second viewport mode, **Chronological overview**, to the existing Timeline editor. Story order remains the default and remains the order of the semantic editor list. The chronological mode organizes items by the meaning and precision of `TimelineItem.event_at`; it does not reorder items or save viewport state as Timeline data.

Implement this slice only after the approved ContentNodes and ContentEdges integration and the Timeline performance design are integrated. Build on that design's bounded editor windows, owner overview, version pinning, drafts, and media mounting rules. Do not edit its design or plan as part of this slice. Add no migration, package, public route, or change to the default full-detail or mutation response contracts.

Assumption: this is an owner-facing navigation and orientation mode in the existing editor. Users continue to describe and reorder items in story order. `TimelineItem.event_at` is the only source for chronological placement; `Asset.captured_at`, upload time, and creation time never fill in a missing event date.

## Alternatives and choice

1. **Map every item to one timestamp.** This is easy to draw, but converting a date-only value to midnight or noon invents precision and can misplace it across time zones.
2. **Resolve each date-only value to an exact UTC day interval with native `Intl`.** `Intl.DateTimeFormat` formats an instant in an IANA zone but exposes no timezone transition table or local-date-to-UTC conversion. A bounded offset-candidate search would rely on an unproven transition assumption for some valid zone/date pairs. Do not claim exact UTC boundaries without a dependable resolver.
3. **Keep calendar dates and exact instants in separate chronological lanes.** This preserves each stored value's precision and ordering semantics without inventing a cross-lane UTC position. It cannot show UTC overlap or total-order a date-only value against an exact instant.

Choose option 3. The chronological mode still gives users a date-ordered lane and an instant-ordered lane, plus a separate undated group. The UI explicitly says that a date-only event and an exact instant are not comparable on one UTC scale. This is the deliberate precision-preserving tradeoff; it keeps the requested chronological navigation useful without implying a time the data does not contain.

## Event-time and coordinate contract

The existing `EventAt` contract in `src/timeline/validation.ts` is authoritative: `date` values carry an ISO date, `calendar: "iso8601"`, and `time_zone`; `instant` values are offset-aware and normalized to UTC, with their display `time_zone` retained. Coordinates are derived for rendering only and are never written back.

- **Calendar-date lane:** map the stored ISO date to an integer proleptic-Gregorian day ordinal, counted from `1970-01-01` using integer calendar arithmetic. The existing four-digit ISO-date schema domain (`0000-01-01` through `9999-12-31`) fits safely in an integer. Each item is a half-open civil-date band `[dayOrdinal, dayOrdinal + 1)`. This is a layout interval on the calendar-label axis, not an elapsed-time or IANA-zone interval: one coordinate unit means one ISO calendar date, not 24 elapsed hours, and `dayOrdinal + 1` is always defined by Gregorian arithmetic even if that labeled date was skipped in the event's timezone. Do not parse a bare date with `Date.parse`, involve the host timezone, resolve a local midnight, or convert the saved date to an instant. Keep and show the stored `time_zone` on each event; it remains event context and does not change this lane's date-label ordering.
- **Exact-instant lane:** map the normalized offset-aware `instant` to its UTC epoch-millisecond point. The supported coordinate domain is the finite ECMAScript `Date` time range, `[-8.64e15, 8.64e15]` milliseconds. Reject an invalid or out-of-range instant instead of clamping it. UTC axis ticks provide one common scale; the saved `time_zone` controls the event label.
- **Undated group:** `event_at: null` appears outside both axes in a labeled **Undated** group. It never receives a coordinate from `Asset.captured_at`, upload time, or `position`.

The date band's key is the stored calendar label. Build logical date groups by `(dayOrdinal, time_zone)` so timezone context is retained. The date lane's coordinate and relative ordering represent ISO date labels only; for equal labels with different zones, timezone string then stable ID is a deterministic presentation tie-break, not event-time ordering. At coarse zoom, pixel bins may combine nearby groups; each grouped chooser entry still shows its full date and timezone, and the accessible group label announces its count and date range. Exact instants are ordered by UTC epoch. There is no cross-lane overlap, tie-break, or order claim. Within the exact-instant lane, equal points are grouped deterministically by stable item ID. Within the date lane, presentation order is `(dayOrdinal, time_zone, id)`. `TimelineItem.position` is never a chronological tie-break; expose its story ordinal separately wherever an item is named or focused.

Keep the coordinate helpers pure and dependency-free. They validate the projected `EventAt` values and return either a calendar-date band, exact point, or undated result. The existing schema validates timezone identifiers; the date lane deliberately performs no timezone-boundary resolution. DST gaps/folds, historical offset changes, a skipped stored date, or an absent next local date therefore cannot make its coordinate unavailable or require a guessed boundary, search horizon, `Intl` resolver, or failure fallback. A malformed projected value fails the page clearly instead of being coerced into a coordinate or reported as undated.

## Read path and access

Reuse the performance design's authenticated, owner-scoped paged overview read. Add an explicit optional projection selector, for example `projection=chronological`:

- Without the selector, keep the performance read's `{ id, position }` rows and response shape unchanged.
- With the selector, return `{ id, position, event_at }` rows. Include no caption, asset metadata, or media URL. Keep the existing full `GET /api/timelines/:id` representation unchanged.
- Both projections use the same 1–1,000 row limit, exact count, timeline summary, snapshot version, and keyset pagination. Pages remain ordered by `(position, id)` in story order; the client builds the date and instant indexes only after all pages for that snapshot arrive.
- Bind a continuation cursor to the timeline, projection, and exclusive `(position, id)` key. A cursor from the story projection cannot be reused for the chronological projection. Every continuation uses its required pinned version.
- For each first page, continuation, and inclusive lower-bound read, get the owner-scoped Timeline/version row and requested projection in the same D1 read batch. Compare the requested version with that row and return 409 with no rows on mismatch. Never combine pages or projections from different versions.

Keep the authenticated Timeline route, current owner visibility of moderated content, and current `404` for another owner. Responses remain private and `no-store`. Do not change anonymous access, public Timeline rendering, media authorization, or moderation rules. The overview projection contains only the minimum owner-authorized metadata needed to position markers.

## Viewport and editor behavior

The mode control is in the viewport toolbar. Story mode remains selected by default and continues to use narrative positions as its logical coordinates. Chronological mode shows two separately labeled and independently controlled tracks: **Calendar dates** and **Exact instants**. A short explanation states that their coordinates preserve different precision and are not cross-comparable on a UTC axis. Undated items remain in a separate labeled group. The editor's ordered list, item ordinals, move controls, reorder payload, and keyboard/touch list navigation always follow `(position, id)`.

Keep separate in-memory viewport state for story positions, calendar-day ordinals, and UTC instants. Each track has its own zoom, pan, measurement, and Fit all controls. The first visit to a track fits its full bounds after its complete index is loaded and the viewport has a nonzero measurement. Later visits restore that track's previous view. A user pan, zoom, or Fit all makes that track's frame manual. Resize preserves the focal coordinate and scale. Appends, page arrivals, event-date edits, and mode switches preserve manual frames; a newly added or edited event may land outside the visible range. Fit all applies only to the track whose control is activated. Changing Timeline resets all three frames.

Store active selection and editor focus by stable item ID, never by a date, instant, or chronological array index. Map a selected chronological marker or marker group back to its story ordinal through the ID index before opening the relevant bounded editor window. If an event-date edit moves an item between lanes or to another coordinate, keep the same item selected and keep its editor fields focused. Keep unsaved caption/date/kind/time-zone drafts in the performance design's editor-level map keyed by ID; switching modes, changing windows, reloading after 409, or re-sorting markers must not clear them. A remote removal keeps a dirty draft in the existing unresolved-draft area.

Build the indexes once per accepted snapshot, not during each pan/zoom render. The date index stores one civil-day unit bands sorted by `(dayOrdinal, time_zone, id)`. A date row's clipped-span midpoint is monotonic in `dayOrdinal`: for viewport world range `[left, right)`, clip `[dayOrdinal, dayOrdinal + 1)` to that range and map the clipped endpoints linearly to pixels. Rows wholly before the viewport have midpoint `-Infinity`; rows wholly after it have midpoint `+Infinity`. Equal dates retain the timezone/ID tie order. This monotonic key permits binary search for the first row assigned to a pixel bin without enumerating all visible rows. The instant index is sorted by `(epochMs, id)` and the matching numeric coordinate array is built with it. Reuse the performance design's occupied 48-pixel-bin helper for exact points; do not materialize all visible points during a render.

The chronological renderer is bounded by the viewport's occupied 48-pixel bins, including Fit all on 10,000 rows. For each date bin with pixel interval `[x0, x1)`, use two binary searches on the date index for (a) rows whose clipped half-open date band intersects the corresponding world interval and (b) rows whose clipped-span midpoint lies in `[x0, x1)`. Intersection uses `dayOrdinal < worldRight && dayOrdinal + 1 > worldLeft`; the viewport and bins are half-open, so an edge-touch alone is not a hit. The first range yields `spanCoverageCount`, the number of item bands whose clipped spans touch any part of the bin. The second yields a contiguous index range and `itemCount`, the number of unique stable IDs assigned to that bin. Do not use a prefix-maximum-end scan or loop over the candidate rows to obtain either count. Each date bin emits at most one aggregate geometry mark: its span-coverage count preserves the clipped half-open coverage at 48-pixel resolution, while its separate midpoint count is chooser membership. An item spanning several bins contributes to each intersected bin's coverage count but belongs to exactly one midpoint bin and appears once in a chooser. This keeps geometry and DOM work bounded by the number of occupied bins while preserving exact date labels and stable-ID membership.

Date-bin choices are enumerated only after activation, from the bin's midpoint index range, in `(dayOrdinal, time_zone, id)` order. Return at most 100 IDs per chooser page and read only the requested page; the chooser cursor is local to the accepted projection/frame and is discarded when that frame or snapshot changes. The group label exposes unique item count and first/last stored date; each choice shows its complete stored date and timezone. Exact-point groups use the existing 48-pixel helper and carry their matching contiguous index range so any point chooser is also paged lazily. No item is materialized into a visual marker list during pan/zoom. The **Undated** lane is one aggregate count/control over the `(position, id)`-sorted null-event index, not one marker per item; its chooser is also paged by stable ID, at most 100 items per page, and reads only the requested slice.

This bounded-bin contract supersedes the earlier visible-candidate `O(log n + k)` render/query wording and per-item date-band marks. Since `k` may be 10,000 under Fit all, a renderer that visits all visible rows or mounts one geometry node per row does not satisfy this design.

Ten thousand is the separate performance fixture, not a client or API maximum. Fetch overview pages until `next_cursor` is null; do not silently stop at 10,000. If a page has a transient failure, retry that page at its pinned version. If the server returns 409 because the snapshot changed, discard the mixed index and restart from a fresh first page, then load every page at that new version. Show an incomplete/loading error state until one complete snapshot is ready. The 10,000-row overview mounts no media.

When loading the chronological projection alongside the story index, merge rows by ID only when both projections have the same Timeline ID and version; otherwise discard the mixed snapshot and reload. On a local event-date save, update the known row only after the versioned mutation commits, rebuild the affected lane index, and preserve ID focus and each manual frame. `position` does not change. Existing minimal-write commitment/reconciliation behavior applies to append and version conflicts; never replay a committed append when a chronological page is stale.

Pass the app's access generation into the Timeline screen. Each overview/detail read captures the auth generation, Timeline ID, read generation, and pinned version it belongs to. Abort reads when possible, and apply a page only if all captured identities still match and its version is not older than an already acknowledged commit. Mutations use a separate identity: capture auth generation, Timeline ID, unique mutation-operation ID, and submitted `expected_version`; do not gate an acknowledgement on read generation. Keep each in-flight operation record until its definitive response is handled, even if navigation starts a new read or selects another Timeline.

When an operation's unique ID is still registered and its captured auth generation is current, a received 204 is definitive for that operation regardless of the current read generation or selected Timeline. Synchronously record the operation's committed status and `committed_version = expected_version + 1` in its Timeline-bound mutation record before awaiting any reconciliation read. A read-generation change alone must never discard the acknowledgement. Keep committed version separate from the displayed/read version. For an event-date edit, patch the visible local projection only when it is for the operation's Timeline and its displayed version is exactly the submitted `expected_version`; advance that projection to the operation's committed version. If that projection is older, invalidate it and reconcile; if it is already newer than the committed version, keep the newer snapshot and do not apply the stale local patch. If another Timeline is selected, retain the old operation's commit record without changing the new screen and reconcile it when that Timeline is next active. For append, mark the asset committed and remove it from that Timeline's pending picker selections before the tail read; a committed asset is never replayed because a read became stale. A stale or failed follow-up read cannot erase this acknowledgement. Invalidate older reads and reconcile from a fresh first page; if the tail read returns 409 or fails, pause later writes in the batch and never replay the committed append. A mutation 409 means no commit and follows the draft-preserving refresh path. A response from an old auth generation cannot alter the current screen or its private state. On logout or a current-generation 401/403, clear Timeline summary, overview pages, detail windows, media metadata, drafts, picker state, selected ID, and private mutation records; an earlier-generation failure cannot clear newer-session state.

Preserve the existing responsive layout, keyboard controls, focus visibility, reduced-motion behavior, vertical page scrolling, and browser magnification. Keep the mode and track labels, group counts, date precision/timezone, UTC instant labels, and undated items available to keyboard and screen-reader users.

## Binary acceptance

- **Coordinate semantics:** An offset-bearing instant maps to the same UTC epoch regardless of its display zone. A date maps by integer ISO Gregorian arithmetic to exactly `[dayOrdinal, dayOrdinal + 1)`; its timezone label is retained and no timezone conversion, local-boundary search, or bare-date parse occurs. Leap-day and date-domain boundary cases are finite. Dates `2011-12-29` and `2011-12-30` in `Pacific/Apia` remain adjacent calendar-label bands even though `2011-12-30` was skipped locally; neither date requires a representable start/end instant, is moved, converted, or hidden. A historical non-hour timezone label does not alter its stored date coordinate. The UI never depicts a date band as a UTC interval or claims cross-lane overlap/order.
- **Unique clipped groups:** In a browser fixture, a date band whose start is offscreen but whose body intersects the viewport contributes to every touched bin's span-coverage aggregate, clipped at the viewport edge. A visible exact instant remains in the separate UTC lane. A band crossing several 48-pixel bins contributes to each bin's coverage count but its stable ID is assigned once by clipped-span midpoint and appears once in the bounded chooser with the full date and timezone. Adjacent bands obey half-open boundaries, including an endpoint that touches but does not overlap a bin. Coarse bins can combine date/timezone groups; nonempty group counts contain unique IDs. A coverage-only bin with no midpoint member is noninteractive geometry, not a zero-choice group.
- **Undated and provenance:** Null `event_at` appears only in the labeled Undated group. Changing `Asset.captured_at`, upload time, or narrative position cannot change chronological coordinates. Updating `event_at` moves an item within or between lanes while preserving `position`; viewport operations never change `event_at`, `position`, or Timeline version.
- **API compatibility and paging:** Existing full-detail and default overview responses remain unchanged. The chronological projection returns only `{id, position, event_at}` rows, in story keyset order, with at most 1,000 rows per page. A 10,000-item mixed fixture yields 10,000 unique IDs across ten or fewer pages; a 10,001-item fixture yields all rows across exactly eleven pages at a 1,000-row limit, proving there is no 10,000 cap. Other-owner requests return 404. Projection-mismatched cursors are rejected. Stale continuation and lower-bound reads return 409 with no rows, and each page's owner/version check and projection use the same D1 batch. Public visibility and moderation tests remain unchanged.
- **Bounded bin work:** For 10,000 dates visible under Fit all, an instrumented date query performs at most four binary searches per viewport 48-pixel bin (two searches for span coverage and two for midpoint membership), with at most `ceil(viewportWidth / 48)` aggregate date marks and no row enumeration. The total midpoint memberships across bins equals the number of visible stable IDs, each exactly once; span-coverage counts equal the half-open intersection oracle per bin, including clipped edge spans and multi-bin spans. A 10,000-date single-bin chooser reads no more than 100 IDs per page and preserves `(dayOrdinal, time_zone, id)` order. A 10,000-item undated fixture renders one aggregate control and reads no more than 100 `(position, id)`-ordered choices per page. A 10,000-point equal-instant group uses the existing point bins and reads no more than 100 `(epochMs, id)`-ordered choices per page. A sparse 10,000-row fixture proves offscreen rows are excluded by binary search. The instant lane reuses the approved occupied-bin helper and mounts at most one group mark per occupied bin. Sorting and numeric coordinate projection occur once per accepted version, not per pan/zoom. The 100-item interactive and 10,000-item lightweight cases remain separate evidence fixtures.
- **Mode and identity:** Switching story → chronological → story leaves the semantic list in `(position, id)` order, retains active stable item ID and draft values, and restores the prior manual frame for story, date, and instant tracks. Resize and append preserve each manual center/span. Selecting a chronological marker opens the story window by ID; a grouped-marker chooser shows at most 100 choices and maps the selected ID to its correct story ordinal. A successful event-date edit updates the correct lane without changing order, and a concurrent 409 preserves every draft and field focus.
- **Mutation acknowledgement races:** Start an overview refresh while an append or event-date mutation is in flight, then release a 204. Assert the registered operation records exactly `expected_version + 1` before starting reconciliation even though the read generation changed. Return an older page and then a stale tail/chronological 409: the old page cannot overwrite committed state, the committed append leaves pending selections, no replay occurs, unrelated drafts/focus/manual frames remain, and writes stay paused until a current overview and active detail window reconcile. Also switch Timeline while a write is in flight; its 204 is committed to the captured Timeline's operation record but cannot change the newly selected screen, and returning to that Timeline does not replay an acknowledged append. A 409 from the mutation itself records no commit. Old-auth responses cannot update the new screen.
- **Access races:** Delay an overview/detail response, change Timeline or auth generation, then release it; stale reads cannot update markers, drafts, selection, media metadata, or errors. A current-generation authorization failure clears sensitive editor state, while an earlier-generation failure cannot clear a newer session. Version conflicts never mix projections from different versions.
- **Accessibility and evidence:** Keyboard and screen-reader users can identify each active track, grouped marker count/date range, stored date precision/timezone, UTC labels, the explicit lack of cross-lane ordering, undated items, and navigate every item through the story list. Browser checks cover desktop and 375-pixel mobile, focus retention, reduced motion, ordinary vertical scrolling, and browser magnification. Measure the chronological 10,000-row scenario separately using the named-device/raw-trace protocol in the performance design; report observed values without an invented frame-rate or latency threshold.

## Not in scope

Do not build a chronological editor list, auto-detect event dates from media, infer an instant for a date-only value, add a date/timezone migration, change `Asset.captured_at`, introduce a new ordering mutation, or modify public Timeline presentation. A later product decision may revisit a unified date/instant UTC axis with an explicitly supported conversion contract. Hardware measurements and production D1 evidence are implementation gates, not claims established by this design.
